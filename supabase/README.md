# Supabase — content backend + admin

The storefront reads all content through `ContentRepository`
(`src/lib/content/`). It uses **Supabase** when `NEXT_PUBLIC_SUPABASE_URL` and
`NEXT_PUBLIC_SUPABASE_ANON_KEY` are set, and falls back to the in-memory
`MockContentRepository` otherwise — so the public site and the tests run with
no backend. The **admin panel** (`/admin`) requires Supabase to be configured.

## Files

| File | What it is |
| --- | --- |
| `migrations/20260910120000_content_schema.sql` | Tables, indexes, `updated_at` triggers, RLS + public read policies. |
| `migrations/20260910130000_admin.sql` | `admins` allow-list, `is_admin()`, admin read/write RLS, and the `perfume-images` Storage bucket + policies. |
| `seed.sql` | Sample catalogue (the 6 mock perfumes + site settings). Generated by `scripts/generate-supabase-seed.mts`; regenerate with `npm run seed:generate` if the sample data changes. |

The schema stores **image references only** (`perfume_images.path` — a Storage
object key, or an absolute / local URL). No binary data, no 3D models.

## Apply it

### With the Supabase CLI (recommended)

```bash
supabase init          # if you haven't already (creates supabase/config.toml)
supabase link --project-ref <your-project-ref>
supabase db push       # applies both migrations/
psql "$DATABASE_URL" -f supabase/seed.sql   # or: supabase db reset (also runs seed.sql)
```

### Without the CLI

Supabase dashboard → **SQL Editor** → run, in order:
`20260910120000_content_schema.sql`, `20260910130000_admin.sql`, then
`seed.sql`.

## Create an admin

1. **Authentication → Users → Add user** (or `supabase auth admin create-user`).
   Give it an email + password. There is no public sign-up.
2. Add that user to the allow-list:

   ```sql
   insert into public.admins (user_id, note)
   select id, 'founder' from auth.users where email = 'you@example.com';
   ```

3. `cp .env.example .env.local`, fill `NEXT_PUBLIC_SUPABASE_URL`,
   `NEXT_PUBLIC_SUPABASE_ANON_KEY` and `SUPABASE_SERVICE_ROLE_KEY`
   (`SUPABASE_SERVICE_ROLE_KEY` is optional today — no code uses it yet — but
   keep it out of any `NEXT_PUBLIC_` name). `npm run dev`, visit `/admin`.

Revoke access with `delete from public.admins where user_id = '<uuid>';`.

## Security model

- RLS is **on** for every content table + `storage.objects`.
- **Public read**: anon `select` on published perfumes (`is_published = true`)
  and their child rows; all of `site_settings`.
- **Admin read**: signed-in users pass `is_admin()` also see drafts.
- **Writes**: `for all to authenticated using (is_admin()) with check
  (is_admin())` on every content table, and admin-only insert/update/delete on
  the `perfume-images` bucket. Anonymous users and authenticated non-admins
  cannot write anything — enforced by the database, not just the app.
- `is_admin()` is `SECURITY DEFINER` with a fixed `search_path`.
- The app never uses the service-role key for admin writes; it uses the
  signed-in user's session so the RLS policies above are the real gate. The
  `getServiceSupabaseClient()` helper stays `server-only` for future needs.

## Cache

Storefront routes are ISR (`revalidate = 3600`). Every admin write calls
`revalidatePath("/", "layout")`, so settings and catalogue changes appear on
the public site immediately, not after the hour.
